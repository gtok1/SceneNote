# 역할별 산출물 통합

요청한 범위와 역할별 산출물의 경로·날짜를 확인하고 [명세 목차](../../../docs/README.md)에서 관련 확정 요구사항을 찾는다. PM의 화면·스토리·우선순위·예외, 설계의 아키텍처·ERD·RLS, FE의 화면 이동·상태·API 연결, BE의 스키마·함수·권한·외부 API 계약을 대조한다. 전달되지 않은 역할은 `[산출물 없음 — 확인 필요]`로 표시한다.

- [초기 MVP 계획](../../../docs/10_mvp_integration_plan.md)의 6개 핵심 기능과 4주 일정은 초기 MVP를 검토할 때 적용한다. 후속 작업의 범위는 사용자 요청과 해당 기능 명세에서 정한다. 기존 구현은 현황을 확인하는 근거다.
- 확정 D-N을 유지한다. PM·개발팀의 제안이 충돌하면 사용자 가치와 근거 경로를 기록하고, 근거가 같은 경우 작은 범위와 보수적인 일정을 택한다. 결정에 필요한 근거가 없으면 `[확인 필요: @담당자]`와 질문을 남기고 독립 항목을 진행한다.
- 요청 범위 밖의 제안은 후속 검토 항목으로 분리한다. 사용자 데이터 테이블의 RLS가 누락되면 해당 구현의 P0 블로커로 표시한다.
- 기존 통합 문서가 있으면 해당 부분을 갱신한다. 별도 기능 명세가 필요한 경우 [명세 작성 패턴](../../../docs/00_codex_doc_pattern.md)을 따른다.

## 통합 계획 형식

본문은 한국어로 작성하고 테이블·함수·컴포넌트는 코드 이름을 사용한다.

| 순서 | 포함할 내용 |
| --- | --- |
| 1. 개요 | 앱 목적, 대상 사용자, 범위에 포함하거나 제외한 기능 |
| 2. 충돌과 결정 | 항목별 PM·개발팀 입장, 결정, 근거 경로와 영향 |
| 3. 용어 | 통일 용어와 정의, PM·FE·BE에서 사용한 표현 |
| 4. 화면 | 주요 기능, 연결 화면, 우선순위(P0 출시 필수·P1 연기 가능·P2 출시 후) |
| 5. 데이터 모델 | 테이블·주요 컬럼·PK/FK, 데이터 소유자와 읽기·쓰기별 RLS |
| 6. API와 Edge Function | 구분, 이름, 목적, 입력, 출력, 우선순위 |
| 7. 개발 순서 | P0 의존성과 일정. 초기 4주는 기반 → 핵심 기능 → 통합 → QA·배포 준비 순으로 배치하고 기간이 부족하면 조정할 범위를 적는다. |
| 8. 리스크 | 영향도·발생 가능성(높음/중간/낮음), 대응, 담당 역할 |
| 9. 체크리스트 | 환경·인증·데이터·화면·테스트·배포 준비 |

범위 안의 기능마다 화면·데이터·API 대응을 점검하고, 쓰임이 불분명한 테이블이나 대응 데이터가 없는 화면을 확인한다. P0 의존성과 명세 테스트 표의 모든 행이 계획에 반영됐는지 검토한다. 완료 보고에는 변경 문서·결정 근거·미결 사항과 담당자, 실제 검증 결과와 미실행 사유를 남긴다.

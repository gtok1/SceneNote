# 00. 명세서 + Codex 프롬프트 작성 패턴 (템플릿)

> **이 문서는 작업 지시가 아니라 작성 규칙이다.**
> SceneNote에서 구현 명세를 만들 때는 **항상 두 개를 짝으로** 만든다. 실제 구현은 Codex 에이전트가 수행하므로, 사람이 읽는 명세서만으로는 부족하다.
> 새 명세를 쓰기 전에 이 문서를 먼저 읽고, 아래 스켈레톤을 복사해서 채운다.

---

## 1. 산출물 규칙

| 산출물 | 대상 | 어디에 |
|--------|------|--------|
| `docs/NN_<기능>_spec.md` | 사람 | **파일.** 왜 이렇게 하는지. 문제 정의, 설계 결정, 기각한 대안, 엣지 케이스, 테스트 표 |
| Codex 프롬프트 | Codex | **대화 응답 본문.** 무엇을 어떤 순서로 할지. 그대로 복사해 Codex 첫 메시지가 되는 자기완결적 지시문 |

**프롬프트는 파일로 만들지 않는다.** 파일에 써두면 사용자가 다시 열어 복사해야 한다. 응답에 4중 백틱(````) 펜스로 감싸 통째로 출력하고, 펜스 안에서만 3중 백틱을 쓴다. 설명이 필요하면 펜스 바깥에 쓴다.
(`docs/13`~`docs/23`의 `codex_prompt_*.md` 파일들은 이 규칙 이전의 산물이다. 참고용으로 남기되 새로 만들지 않는다.)

**번호 규칙**

- `NN`은 `docs/` 안에서 마지막으로 쓰인 번호 + 1. 명세서 하나당 번호 하나.
- 이미 만든 기능을 고치는 작업이면 새 번호를 쓰되, 제목에 `_fixes` 또는 `_qa_YYYY-MM-DD`를 붙여 원본과 구분한다 (예: `14_codex_prompt_episode_progress_fixes.md`, `21_mobile_usability_qa_2026-09-09.md`).
- 작은 수정이라도 **명세서를 생략하지 않는다.** 1페이지로 줄일지언정 없애지는 않는다. 프롬프트만 주면 왜 그렇게 고쳤는지가 남지 않는다.

**필수 후속 작업**

새 명세서를 만들면 `AGENTS.md`의 "작업 지시 문서 — 항상 먼저 읽기" 표에 **한 줄을 추가한다.** Codex는 `AGENTS.md`를 항상 읽으므로 이 표가 상시 로딩 경로다. 이걸 빠뜨리면 문서가 존재하지 않는 것과 같다.

## 2. 작성 전에 반드시 하는 것

프롬프트의 품질은 조사량에 비례한다. 스켈레톤을 채우기 전에:

1. **실제 코드를 열어 행 번호까지 확인한다.** 프롬프트에 쓰는 모든 파일 경로·행 번호·함수 시그니처·타입 이름은 추측이 아니라 확인한 사실이어야 한다. Codex는 틀린 좌표를 받으면 엉뚱한 곳을 고친다.
2. **영향 경로를 끝까지 따라간다.** "이 값이 잘못됐다"에서 멈추지 말고 그 값이 어느 화면의 어떤 문구로 나타나는지까지 추적한다. 그래야 명세서의 "증상"이 검증 가능해진다.
3. **기존 테스트에 걸 수 있는 앵커를 찾는다.** 이미 있는 테스트에 assertion 두 줄만 더해 실패시킬 수 있으면 그게 최고의 회귀 테스트다.
4. **재사용할 수 있는 기존 함수를 찾는다.** 새 유틸을 만들기 전에 `src/utils/`를 훑는다. 비슷한 게 있으면 확장할지 별도로 둘지 프롬프트에서 명시해야 한다.
5. **수정 범위를 파일 목록으로 확정한다.** 확정하지 못하면 아직 조사가 덜 된 것이다.

## 3. 명세서 스켈레톤 (`docs/NN_<기능>_spec.md`)

```markdown
# NN. <기능> 명세

작성일: YYYY-MM-DD
대상 브랜치 기준: <branch> (<commit>)
선행 문서: docs/..., docs/...

## 1. 문제 정의
무엇이 안 되는지. 사용자가 실제로 겪는 증상으로 쓴다. 결함이 여러 건이면 F-1, F-2... 표로.

## 2. 근본 원인
왜 그런지. 코드 인용 + 행 번호. "증상"이 아니라 "원인"을 쓴다.

## 3. 재현 시나리오
1. ... 2. ... 3. ...  — 번호 매긴 단계. 검증 단계에서 그대로 따라할 수 있어야 한다.

## 4. 설계 결정
### D-1. <결정 한 줄>
근거. 왜 다른 방식이 아닌지.
### D-2. ...
> D-N은 Codex가 임의로 바꾸면 안 되는 항목이다. 바꿔야 한다고 판단되면 구현하지 말고 보고하게 한다.

## 5. 기각한 대안
무엇을 왜 버렸는지. 이게 없으면 나중에 같은 논의를 반복한다.

## 6. 계약 (타입 · 판정 순서)
타입 시그니처와 판정 순서를 번호로. 구현 세부가 아니라 계약만.

## 7. 데이터 모델 / SQL (해당될 때)
마이그레이션 SQL 전문.

## 8. 화면 명세 (해당될 때)
어느 화면의 어느 지점이 어떻게 바뀌는지.

## 9. 엣지 케이스
| # | 상황 | 기대 동작 |
E-1, E-2, ... 표로. 전부 테스트 표와 연결한다.

## 10. 테스트 표
| ID | 입력 | 기대 |
T-1, T-2, ... "모든 행을 테스트로 옮긴다. 줄이지 않는다"를 명시.

## 11. 변경 파일 목록
| 파일 | 변경 |

## 12. 범위 밖
건드리지 않을 것과 그 이유. 이게 없으면 Codex가 "김에" 고친다.

## 13. 확실하지 않음 — 별도 검증 필요 (해당될 때)
외부 API 동작 등 검증하지 못한 가정. CLAUDE.md 설계 원칙 4.
```

## 4. Codex 프롬프트 스켈레톤 (응답 본문에 출력)

펜스 안은 전부 프롬프트다. 사용자용 메타 설명("이 프롬프트는 ~를 위한 것입니다")을 중간에 섞지 않는다.

```markdown
# ROLE & GOAL
너는 SceneNote(React Native + Expo + Supabase) 리포의 구현 담당이다.
<한 문단으로 목표>. <기능 추가인지 정정 작업인지 명시>.
(결함 수정이면 F-1/F-2 표를 여기 넣는다)

# READ FIRST
1. `docs/NN_<기능>_spec.md` — 이 작업의 명세서. 설계 결정 D-N과 엣지 케이스 E-N이 들어 있다.
2. `docs/<선행문서>.md` — <왜 읽어야 하는지>
3. `AGENTS.md` — 테스트 규칙. **테스트 파일에서 React Native나 Supabase 모듈을 import하면 실행이 깨진다.**
4. `<이번에 고칠 핵심 파일>`

# 시작 상태 (반드시 유지)  ← 기존 동작을 깨면 안 되는 작업일 때만
현재 통과하는 테스트 수, 이미 동작하는 기능 목록.

# 바꾸면 안 되는 설계 결정
- **D-N (최우선).** <제일 위험한 제약을 맨 위에>. 어기면 <어떤 버그가 재발하는지>.
- 기존 `<함수명>`은 <어디서> 쓰고 있다. **삭제·시그니처 변경 금지.**
- `<파일>`은 **바꾸지 않는다.**
- DB 마이그레이션을 새로 만들지 않는다. (해당될 때)

# STEP 1 — <실패하는 테스트부터>
결함 수정이면 **항상 테스트를 먼저 쓴다.**
"`npm test`를 돌려 이 테스트가 실패하는 것을 눈으로 확인한다. 실패하지 않으면 시나리오를 잘못 짚은 것이니 멈추고 보고해라."

# STEP 2 — <수정>
교체 전/후 코드를 그대로 보여준다. 주석으로 남길 근거도 프롬프트에 써준다.

# STEP 3, 4, ... — <나머지>
각 STEP은 독립적으로 검증 가능한 단위로 쪼갠다.

# 엣지 케이스 (전부 처리, 명세서 N장)
| # | 상황 | 기대 동작 |

# 검증 명령
순서대로 전부 통과해야 한다.
```
npm test
npm run typecheck
npm run lint
```
`npm test`는 기존 테스트가 하나도 깨지지 않아야 한다 (현재 기준선: N개 통과).

# DEFINITION OF DONE
- [ ] 체크박스로. 각 항목은 객관적으로 판정 가능해야 한다.
- [ ] "T-1이 수정 전에 실패하는 것을 확인했고 수정 후 통과한다"
- [ ] 기존 테스트 개수가 줄지 않았다

# 변경해야 할 파일 (이 외 파일 수정 금지)
```
경로1
경로2
```

# 보고 항목
1. 실패했던 테스트의 실제 출력
2. `npm test` 결과 (before / after 통과 개수)
3. `npm run typecheck`, `npm run lint` 결과
4. 추가한 테스트 ID와 이름
5. D-N 중 문제가 있다고 판단한 항목 (바꾸지는 말고 보고만)
6. 배포·마이그레이션 등 사람이 해야 할 후속 작업

# 금지사항
- 배포 명령(`npx supabase functions deploy` 등)을 실행하지 않는다. 배포는 사람이 한다.
- DB 마이그레이션 파일을 만들지 않는다. (해당될 때)
- 테스트 표의 행을 임의로 줄이지 않는다.
- **테스트를 통과시키려고 assertion을 완화하지 않는다. 구현을 고친다.**
- 리팩터링·포맷팅·"김에 고치기"를 하지 않는다. 명시된 변경만 한다.
- 테스트 파일에서 React Native 모듈(`react-native`, `expo-*`)이나 Supabase 클라이언트를 import하지 않는다. 타입만 `import type`으로 가져온다.
```

## 5. 모든 프롬프트에 들어가는 프로젝트 고정 사항

아래는 SceneNote에서 매번 동일하므로 그대로 복사해 넣는다.

**검증 명령**
```
npm test          # tsx --test, src/**/*.test.ts · scripts/**/*.test.ts · supabase/functions/**/*.test.ts
npm run typecheck
npm run lint
```

**테스트 제약 (AGENTS.md)**
- `node:test` + `node:assert/strict`를 쓴다.
- 테스트 파일에서 React Native나 Supabase 모듈을 import하면 실행이 깨진다. **순수 함수만 테스트한다.**
- 그래서 화면 파일에 판정 로직을 인라인으로 두면 안 된다. `src/utils/`의 순수 함수로 빼야 검증할 수 있다.
- 테스트 글롭은 `.ts`만 잡는다. `.tsx`와 `app/`은 테스트되지 않는다.

**개발 서버**
- Expo 웹은 반드시 `8081` 포트만 쓴다. `npm run web -- --port 8081 --localhost --clear`
- 8081이 사용 중이면 다른 포트로 우회하지 말고 기존 서버를 확인하거나 종료 후 같은 포트로 다시 띄운다.

**아키텍처 불변 사항 (CLAUDE.md)**
- 외부 API 키는 클라이언트에 노출하지 않는다. TMDB·AniList·Kitsu·TVmaze 호출은 Edge Function 경유.
- 콘텐츠 메타데이터 테이블과 사용자 기록 테이블을 분리한다. 사용자 기록 테이블은 RLS 필수.
- 핀 저장값은 문자열이 아니라 정수 초 `timestamp_seconds`.
- 서버 데이터는 TanStack Query, UI 상태는 Zustand/Jotai.

## 6. 자주 어긋난 지점 (실제로 겪은 것들)

| 함정 | 대응 |
|------|------|
| 프롬프트가 "고쳐줘"로 끝나서 Codex가 증상만 덮음 | 근본 원인과 **판정 순서**를 계약으로 박는다. "이 조건에서는 절대 폴백하지 않는다" 같은 부정 제약을 명시 |
| Codex가 테스트를 통과시키려고 assertion을 약화 | 금지사항에 명시. DoD에 "기존 테스트 개수가 줄지 않았다" 포함 |
| 수정 전에 실패하지 않는 테스트를 "회귀 테스트"라고 추가 | STEP 1을 항상 "실패를 눈으로 확인" 단계로. 실패 안 하면 멈추고 보고하게 한다 |
| Codex가 "김에" 주변 코드를 리팩터링 | **변경 가능 파일 화이트리스트**를 준다. 그 외 수정 금지 |
| 테스트를 `.tsx`나 `app/` 아래 만들어서 아예 실행되지 않음 | 순수 함수로 분리하고 `src/utils/*.test.ts`에 두라고 지시 |
| 테스트 파일이 RN을 import해서 러너가 깨짐 | 타입은 `import type`으로만. 금지사항에 명시 |
| Codex가 Edge Function을 배포해버림 | 금지사항에 배포 명령 명시. 보고 항목에 "재배포가 필요하다는 점"만 남기게 한다 |
| 행 번호가 틀려서 엉뚱한 곳을 고침 | 프롬프트 작성 직전에 실제 파일을 열어 좌표를 확인한다 |
| 명세서만 만들고 AGENTS.md 표를 빠뜨림 | 명세서를 만든 직후 바로 한 줄 추가 |
| 프롬프트를 파일로 만들어서 사용자가 다시 열어 복사해야 함 | 프롬프트는 **응답 본문**에 바로 출력한다 |

## 7. 마무리 체크리스트

- [ ] `docs/NN_<기능>_spec.md`가 있다
- [ ] 프롬프트를 **응답 본문에** 4중 백틱 펜스로 통째로 출력했다 (파일로 만들지 않았다)
- [ ] 펜스 안에 사용자용 메타 설명이 섞여 있지 않다
- [ ] 프롬프트에 ROLE & GOAL · READ FIRST · 바꾸면 안 되는 설계 결정 · STEP · 검증 명령 · DoD · 변경 파일 목록 · 보고 항목 · 금지사항이 모두 있다
- [ ] 프롬프트만 읽고도 잘못 구현할 수 없을 만큼의 계약(타입 시그니처, 판정 순서, 테스트 표)이 프롬프트 **안에** 있다
- [ ] 모든 파일 경로·행 번호·함수명을 실제 코드에서 확인했다
- [ ] 테스트 표의 모든 행이 엣지 케이스와 연결되어 있다
- [ ] `AGENTS.md` 표에 명세서 한 줄을 추가했다
- [ ] 명세서에 "범위 밖"과 "기각한 대안"이 있다

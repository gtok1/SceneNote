# Codex 작업 요청: "지금 많이 찾는 작품" 추천 알고리즘 개선

## 배경

홈의 인기 추천 섹션은 아래 파이프라인으로 동작한다:

1. **서버** `supabase/functions/popular-recommendations/index.ts`
   - 드라마: TMDB `/trending/tv/week` + `/discover/tv`(KR·JP, genre 18)
   - 애니: AniList 트렌딩 GraphQL + 상위 20개만 TMDB 한국어 메타데이터 보강
   - 사용자 라이브러리 보유작 제외 → 방영 연월 내림차순 정렬 → 풀 30개 반환
   - 사용자별 인메모리 캐시 5분
2. **클라이언트** `src/services/popularRecommendations.ts`
   - 응답 정규화 + 한국어 제목 fallback(하드코딩 오버라이드 맵)
   - 풀 부족/실패 시 하드코딩 작품명 목록으로 검색해 채움(fallback)
3. **클라이언트** `src/components/content/PopularRecommendationSection.tsx`
   - `air_year === 올해` 필터 + 라이브러리/추가됨/제외 필터 → Top 10 표시
   - 새로고침 시 풀 30개 안에서 10개씩 회전
   - 제외 상태: `src/stores/recommendationUiStore.ts` (로컬 영구 저장)

확인된 문제:

- **P1. 인기 신호 미사용**: 최종 정렬(`compareRecommendationRecency`,
  서버 697~711행 부근)이 방영 연월만 사용한다. TMDB `popularity`와 AniList
  트렌딩 순위를 받아놓고 버리므로, 최신 무명작이 지난달 화제작보다 항상 상위다.
  "지금 많이 찾는 작품" 라벨과 알고리즘이 불일치.
- **P2. 달력 연도 필터**: 서버 `isWithinCandidateYears`(candidate_years=1이면
  올해만)와 클라이언트 `isCurrentRelease`(`air_year === 올해`)가 달력 연도
  기준이라, 1월이 되면 12월 방영작이 전부 탈락해 추천이 거의 빈다.
- **P3. 하드코딩 fallback**: `FALLBACK_QUERIES`(2026년 6~7월 작품명 약 50개)와
  `KOREAN_TITLE_OVERRIDE_ENTRIES`(약 30개)가 클라이언트에 하드코딩. 다음 달부터
  낡고, P2와 결합하면 연초에 전멸한다.
- **P4. 비효율 캐시**: 서버 캐시 키가 사용자별(`userId:...`) + 인메모리라 히트율이
  낮고, 요청마다 애니 한국어 보강으로 TMDB 호출이 최대 40~60회 병렬 발생.
  그런데 사용자별 요소(라이브러리 제외)는 클라이언트 `createVisibleRecommendations`가
  `libraryKeys`로 **이미 중복 수행**하므로 서버 응답이 사용자별일 이유가 없다.
- **P5. 드라마 후보 조건 과협소**: `normalizeTmdbDrama`가 genre 18(Drama) 미보유
  작품을 무조건 탈락시켜, 스릴러/미스터리로만 태깅된 정당한 화제작이 빠질 수 있다.
- **P6. 제외 되돌리기 없음**: `recommendationUiStore`에 `excludeRecommendation`만
  있어 실수로 제외하면 영구적이고, 제외가 쌓이면 풀이 마른다.

작업 A~E로 나눈다. A가 알고리즘 핵심이며, A와 B는 같은 Edge Function을
수정하므로 A → B 순서를 지킨다. C, D, E는 순서 무관.

## 작업 A. 인기 점수 기반 정렬 + 롤링 윈도우 (P1 + P2)

### 구현 지시

1. **인기 신호 보존**:
   - TMDB 응답의 `popularity`(number)를 `TmdbTvItem`에 추가하고
     `normalizeTmdbDrama`에서 보존한다.
   - AniList 응답에는 명시적 점수가 없으므로 **트렌딩 응답 내 순서**(index)를
     인기 순위로 사용한다 (`trendingIndex`로 보존).
   - `PopularRecommendation`에 내부 계산용 필드를 추가하되, 클라이언트 응답
     스키마 변경은 최소화한다 (rank 의미가 바뀌는 것이 핵심).
2. **가중 정렬로 교체** (`rankRecommendations` / `compareRecommendationRecency`):
   - 소스별 인기 정규화: 카테고리 내 인기 순위를 0~1로 변환
     (1위=1.0, 꼴찌=0.0). TMDB는 `popularity` 내림차순 순위, AniList는
     `trendingIndex` 오름차순 순위 기준.
   - 최신성 부스트: 방영일이 오늘 기준 28일 이내면 ×1.5, 29~90일이면 ×1.2,
     그 외 ×1.0. (계수는 상수로 분리해 조정 가능하게)
   - 최종 점수 = 정규화 인기 × 최신성 부스트, 내림차순 정렬.
   - 동점이면 방영일 최신 우선, 그다음 기존 순서 유지.
3. **롤링 윈도우 필터로 교체** (P2):
   - 서버: `isWithinCandidateYears`(연도 기준)를 `air_date` 기준
     **최근 180일 ~ 오늘(+당월 말)** 윈도우로 교체. `candidate_years` 파라미터는
     하위 호환을 위해 받되 윈도우 일수로 환산(1년=365일)하거나, 파라미터를
     `candidate_days`로 대체하고 클라이언트 호출부를 함께 수정한다.
     air_date가 없고 air_year만 있는 항목은 해당 연도가 윈도우와 겹치면 통과시킨다.
   - 클라이언트: `isCurrentRelease`(air_year === 올해)와
     `createVisibleRecommendations`의 동일 필터를 같은 윈도우 규칙으로 교체.
4. **정렬/필터 로직 단일화**:
   - 순수 함수(점수 계산, 윈도우 판정)를 서버는
     `supabase/functions/_shared/popularRanking.ts`(신규)로, 클라이언트는
     `src/utils/popularRanking.ts`(신규)로 분리한다. Deno/RN 간 코드 공유가
     안 되므로 파일은 두 개지만 **로직과 테스트 케이스를 동일하게** 유지하고,
     각각 `*.test.ts`를 작성한다 (기존 `src/utils/upcomingAiring.test.ts`,
     `supabase/functions/_shared/recommendationEngine.test.ts` 스타일 참고).

### 수용 기준

1. 같은 풀에서 "지난달 인기 1위 작품"이 "이번 달 인기 최하위 작품"보다 위에 온다.
2. 최근 28일 내 방영작은 같은 인기라면 오래된 작품보다 위에 온다.
3. 12월 31일→1월 1일 경계를 시뮬레이션한 단위 테스트에서 12월 방영작이
   여전히 후보에 포함된다.
4. `npx tsc --noEmit`, `npx eslint .`, `npm test` 통과.

## 작업 B. 전역 캐시 전환 + 보강 결과 DB 캐시 (P4)

### 구현 지시

1. **서버 응답을 사용자 무관하게**:
   - `getUserLibraryExternalKeys` 호출과 서버 측 라이브러리 제외를 제거한다.
     (클라이언트 `createVisibleRecommendations`가 동일 필터를 이미 수행함을
     확인했다 — 제거 전 해당 코드가 실제로 커버하는지 재확인할 것)
   - 캐시 키에서 `userId`를 제거한다.
2. **`external_search_cache` 테이블로 캐시 이전**:
   - 인메모리 Map 대신 기존 `external_search_cache` 테이블에
     키 예: `popular-recommendations:v2:{windowDays}:{poolLimit}`, TTL 30분으로 저장.
     테이블 스키마(키/만료 컬럼)는 `search-content` 함수의 기존 사용 방식을
     따른다. 인메모리 캐시는 같은 인스턴스 내 단기 캐시로 유지해도 된다.
3. **애니 한국어 보강 결과 캐시**:
   - `enrichAnimeWithTmdbKorean` 결과(한국어 제목/포스터/줄거리)를
     `external_search_cache`에 AniList ID 키(`anilist-ko:{id}`), TTL 7일로 저장하고
     보강 전에 캐시를 먼저 확인한다.
   - 캐시 도입 후 보강 대상을 상위 20개 제한(`ANIME_KOREAN_ENRICHMENT_LIMIT`)에서
     **풀 전체(30개)** 로 확대한다 (21~30위가 영어 제목으로 노출되는 문제 해결).
   - 동시 TMDB 호출은 최대 5개로 제한한다 (간단한 세마포어/청크 처리).

### 수용 기준

1. 서로 다른 두 계정이 30분 내 연속 호출하면 두 번째 호출은 외부 API를 타지 않는다
   (로그로 확인).
2. 애니 풀 30개 전부 한국어 제목(가능한 경우)으로 반환된다.
3. 같은 응답에 대해 클라이언트 표시 결과(보유작 제외)가 작업 전과 동일하다.
4. RLS: `external_search_cache` 쓰기는 service_role로만 수행된다.

## 작업 C. fallback을 "마지막 성공 응답 캐시"로 교체 (P3)

### 구현 지시

1. `src/services/popularRecommendations.ts`에서:
   - 서버 응답 성공 시 응답 전체를 AsyncStorage
     (`scenenote-popular-recommendations-last-good`, 저장 시각 포함)에 저장한다.
   - 서버 호출 실패 시 하드코딩 검색 fallback 대신 저장본을 반환하고,
     응답에 `stale: true`(또는 기존 `partial` 활용)를 표시한다.
   - 저장본이 없을 때만 최소한의 검색 fallback을 유지하되, 목록은
     작품명 하드코딩이 아니라 **TMDB discover 호출을 그대로 쓰는
     `search-content` 계열 일반 검색**으로 대체 가능한지 확인하고, 불가하면
     빈 상태 UI(EmptyState + 재시도)로 처리한다.
2. `FALLBACK_QUERIES`, `KOREAN_TITLE_OVERRIDE_ENTRIES` 및 관련 함수들을 삭제한다.
   (작업 B의 보강 확대가 선행되면 오버라이드 맵 없이도 한국어 제목이 채워진다 —
   B 미적용 상태로 이 작업을 하게 되면 오버라이드 맵은 남겨두고 보고에 명시)
3. UI: stale 데이터 표시 시 섹션에 "오프라인 저장본" 배지나 안내 문구를 추가한다
   (`PopularRecommendationSection.tsx`).

### 수용 기준

1. 네트워크 차단 상태에서 홈 진입 시 마지막 성공 목록이 표시되고 stale 표시가 보인다.
2. 하드코딩 작품명 목록이 코드베이스에서 제거된다 (또는 예외 사유 보고).
3. 최초 실행(저장본 없음) + 서버 실패 시 크래시 없이 빈 상태 UI가 나온다.

## 작업 D. 드라마 후보 조건 완화 (P5)

### 구현 지시

1. `normalizeTmdbDrama`의 "genre 18 필수" 조건을 제거하고 **제외 방식**으로 교체:
   - 제외 장르: 16(Animation), 10763(News), 10764(Reality), 10767(Talk)
   - 국가 조건(KR/JP → kdrama/jdrama 분류, `inferTmdbTvContentType`)은 유지
2. `/discover/tv` 호출 파라미터의 `with_genres: "18"`도 같은 기준으로 조정:
   `with_genres` 제거 + `without_genres: "16,10763,10764,10767"`.
3. 조정 후 실제 응답 품질을 확인한다: 로컬에서 함수를 실행해 드라마 풀 30개를
   출력하고, 예능/뉴스가 섞이는지 눈으로 검증한 목록을 보고에 첨부한다.
   품질이 나빠지면(비드라마 유입) `with_genres` 복원 + 트렌딩 경로만 완화하는
   절충안으로 후퇴하고 사유를 보고한다.

### 수용 기준

1. 예능/토크/뉴스가 풀에 등장하지 않는다.
2. 조정 전 대비 풀 후보 수가 같거나 늘어난다 (검증 로그 첨부).

## 진행 순서 및 공통 사항

- 순서: **A → B** (같은 Edge Function 수정, 순서 고정) → C → D → E.
  C는 B 완료 후 진행을 권장 (오버라이드 맵 삭제 조건).
- 각 작업 별도 커밋. Edge Function 변경(A, B, D)은 로컬
  `npx supabase functions serve`로 실행해 실제 응답을 확인한 결과를 보고에 포함.
- 정렬 상수(부스트 계수, 윈도우 일수)는 파일 상단 상수로 모아 조정 가능하게 유지.
- `npx tsc --noEmit`, `npx eslint .`, `npm test` 통과.
- 이 작업은 별도 진행 중인 개인화 추천(`personalized-recommendations`)과
  독립적이다. 해당 기능의 파일을 수정하지 말 것.

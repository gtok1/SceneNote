# 28. 검색 추천 스크롤 추가 로딩 회귀 수정 명세

작성일: 2026-09-24  
대상 브랜치 기준: main (`ca4e285`, 미커밋 변경 포함)  
선행 문서: `docs/11_screen_implementation_spec.md`, `docs/22_search_recommendations_restore_spec.md`, `docs/27_excluded_relationship_themes_spec.md`

## 1. 문제 정의

검색 탭의 빈 검색어 상태에서 추천 카드 끝까지 스크롤해도 다음 작품이 자동으로 붙지 않는다. 계정별 제외 설정으로 첫 배치에서 7개만 남은 화면은 하단에 **“추천 더 찾기”** 버튼을 노출한다. 사용자는 스크롤로 다음 추천을 이어 보길 원한다. 명시적 제목 검색의 페이지네이션은 이번 결함이 아니다.

## 2. 근본 원인

`app/search.tsx`의 추천 `ListFooterComponent`는 `emptyContinuationStopped && activeRecommendations.length > 0`일 때 수동 버튼을 렌더한다(작성 당시 900~908행). 같은 파일의 `onEndReached`는 `shouldAutoLoadNextRecommendationBatch`에 위 상태를 넘기고, `src/utils/recommendationFeed.ts`의 해당 함수는 보이는 카드가 12개 미만이거나 자동 보충이 중단됐으면 `false`를 반환한다. 따라서 필터로 7개가 남고 짧은 배치를 채우기 위한 제한된 자동 탐색이 끝나면, 커서가 살아 있어도 추가 스크롤은 진행할 수 없다. 이 상한 자체는 공급자에서 빈 배치가 계속 올 때 무한 요청을 막는 데 필요하다.

실제 추가 로딩 요청에서는 별도 HTTP 400 `INVALID_REQUEST`도 확인됐다. `usePersonalizedRecommendations.ts`가 누적된 원시 추천 카드의 canonical/external/title 별칭 전부를 `excludeIds`로 넘기고, `personalizedRecommendations.ts`는 중복 제거만 해 `exclude_ids`를 전송한다. Edge Function의 `MAX_EXCLUSION_IDS=200`(`supabase/functions/personalized-recommendations/index.ts`)을 초과하면 요청이 거부된다. 화면에서 숨긴 후보도 원시 목록에 남아 있으므로 필터 계정에서 이 상한에 빨리 도달한다.

## 3. 재현 시나리오

1. 관계 테마 제외 설정이 켜진 계정으로 로그인하고 검색어를 비운다.
2. 추천 후보 일부가 필터링되어 화면에 12개 미만(예: 7개)이 남고, 응답에는 다음 커서가 있다.
3. 카드 끝까지 스크롤하면 “추천 더 찾기” 버튼을 눌러야 다음 탐색이 시작된다.

## 4. 설계 결정

### D-1. 다음 배치는 실제 스크롤 도달로 자동 요청한다

추천 목록 하단에 사용자가 도달하고 다음 커서가 유효하면 `loadMore`를 호출해 **기존 카드 아래에** 붙인다. 보이는 카드가 12개보다 적어도 동일하다. 정상 흐름에서 별도 “더 찾기” 클릭을 요구하지 않는다. 새 추천 12개 버튼은 기존처럼 새 배치로 갱신하는 별개 동작이다. `docs/22` D-2의 일반 제목 검색과 유사 검색은 기존 흐름을 유지한다.

### D-2. 요청·오류·종료 상태는 한 번만 판정한다

초기 조회, 갱신, 빈자리 보충, 추가 로딩 중에는 중복 요청하지 않는다. 오류가 나면 기존 카드를 유지하고 오류 및 **다시 시도** 버튼을 보인다. `is_exhausted`, `has_more=false`, 커서 없음이면 자동 요청하지 않고 종료 문구를 보인다. 기존 cursor, 계정 범위, 중복 제거, 12개 배치 계약은 유지한다.

### D-3. 필터 후 12개 미만과 진전 없는 탐색을 구분한다

계정별 필터로 짧아진 첫 배치는 기존 제한(연속 탐색 횟수·경과 시간) 안에서 자동 보충한다. 상한에 닿아도 다음 커서가 있으면 **새로운 실제 사용자 스크롤 동작으로** 한 번의 제한된 탐색을 다시 시작할 수 있다. 레이아웃 변경이나 같은 하단 도달 콜백 반복만으로 재시작하지 않는다. 커서가 진전하지 않거나 새로 보이는 작품이 계속 0개면 무한 로더를 멈추고 현재 작품을 유지하며 설명·수동 재시도만 보조 수단으로 둔다. 자동 호출의 각 주기는 유한해야 한다.

### D-4. 필터·화면 문맥을 바꾸지 않는다

현재 로그인 계정의 제외 테마·장르를 추가 배치에도 그대로 적용한다. 설정을 읽기 전, 로그아웃, 계정 전환, 탭 이탈, 명시적 제목/유사 검색에서는 추천 추가 로딩을 시작하지 않는다. 앞선 계정·화면의 늦은 응답은 현재 목록에 합치지 않는다. 추천 필터를 검색 결과나 라이브러리에 확장하지 않는다(`docs/27` D-5·D-7).

### D-5. 갤러리 카드의 하단 행동 위치를 고정한다

`PersonalizedRecommendationGalleryCard.tsx`의 footer(작성 당시 85~123행)는 관심 없음·비슷한 작품·선택적 요소 줄이기·빠른 보기와 추가 행동으로 구성된다. `onReduceTheme` 유무에 관계없이 아이콘 슬롯의 폭과 순서, 빠른 보기 위치, 추가 버튼의 폭과 수직 위치를 일관되게 유지한다. 요소 줄이기를 제공하지 않는 카드에는 조작할 수 없는 빈 슬롯만 두며 가짜 버튼을 노출하지 않는다. 모든 실제 행동의 터치 영역은 최소 44×44pt이고 좁은 화면이나 긴 문구에서 버튼이 잘리거나 카드마다 다른 줄에 밀리지 않아야 한다.

### D-6. 요청의 제외 ID만 최대 200개로 제한한다

`src/utils/recommendationSession.ts`의 계정별 전체 seen 기록은 잘라내지 않는다. **전송 직전** ID를 정규화·중복 제거한 뒤 최근 항목부터 최대 200개만 `exclude_ids`에 넣는다. 최초 노출 기록이나 로컬 중복 판정에 쓰는 전체 history는 그대로 유지한다. 추천 새로고침·빈자리 보충·추가 로딩 등 제외 ID를 보내는 모든 경로에 같은 상한을 적용한다. 서버 제한을 늘리거나 별칭을 전부 제거하지 않는다. 200개 밖의 오래된 작품이 서버에서 다시 와도 클라이언트의 기존 identity 중복 제거가 표시 목록에 재추가하지 않아야 한다.

## 5. 기각한 대안

| 대안 | 기각 사유 |
|---|---|
| 정상 페이지마다 “추천 더 찾기” 버튼 유지 | 사용자의 스크롤 연속 탐색 요구를 충족하지 못한다 |
| 빈 배치면 상한 없이 자동 재호출 | 필터된 후보·외부 API 오류에서 무한 요청과 로더가 재발한다 |
| 12개가 보일 때만 다음 페이지 요청 | 스크린샷처럼 필터 후 7개인 피드가 막힌다 |

## 6. 계약 및 화면

판정 순서: **추천 모드·로그인·설정 준비·화면 활성/온라인** → **유효 커서와 미종료** → **오류/중복 요청 없음** → **하단에 대한 새 사용자 스크롤 또는 아직 남은 초기 자동 보충 예산** → 요청. `loadMore`의 결과는 기존 `appendRecommendationFeed`의 identity 중복 제거로 붙인다. 실패·상한 도달은 로더를 끝내고 설명한다. 성공 후에도 다음 커서가 있으면 다음 *사용자 스크롤*에서 이어 간다.

목록 하단은 로딩 중 진행 상태, 오류 시 재시도, 실제 종료 시 종료 문구를 표시한다. 정상적인 다음 배치가 있는 상태에는 “추천 더 찾기” 버튼을 표시하지 않는다. 필터로 후보가 줄었다는 설명은 유지한다. 추천 카드 footer는 선택적 테마 행동의 유무에도 동일한 정렬·터치 영역을 유지한다.

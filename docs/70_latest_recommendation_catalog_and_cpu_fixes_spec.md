# 70. 최신 추천 수집·페이지 순서와 546 CPU 오류 정정

작성일: 2026-11-15
선행 문서: [00 UI](00_ui_style_rules.md), [11](11_screen_implementation_spec.md), [27](27_excluded_relationship_themes_spec.md), [28 §10](28_recommendation_scroll_pagination_fixes_spec.md#10-2026-11-15-사용자-승인--추천-전체-공개일-최신순), [33](33_kr_ott_availability_spec.md), [41](41_taste_fill_recommendations_spec.md), [43](43_recommendation_add_misclick_fixes_spec.md), [47](47_recommendation_batch_topup_spec.md), [52](52_recommendation_first_batch_fill_spec.md), [64](64_recommendation_invocation_cost_fixes_spec.md), [69](69_persistent_public_metadata_cache_fixes_spec.md).

## 1. 문제 정의

사용자가 빈 검색 화면에서 국가 일본/한국을 선택해 최신순으로 탐색했으나 24개 안에 1981년 작품까지 나오고, 다음 조회가 HTTP546으로 실패했다. 사용자는 날짜 표시만 정렬하는 것이 아니라 **최신 공개작부터 조건에 맞는 작품을 이어 찾는 동작**을 요구한다.

## 2. 확인한 원인

- 현재 화면은 일반 제목 검색이나 국가 browse가 아니라 개인화 추천이다. 국가 필터는 최근 기간을 뜻하지 않는다.
- docs/28 §10은 현재까지 받은 결과만 정렬했다. 서버는 월 카탈로그가 요청 시간 한도로 12개를 못 채우면, 최신 월 탐색이 남아 있어도 `popularity.desc`·기간 제한 없는 취향 보충으로 자리를 채운다(docs/41·52).
- 기존 공급자도 월 안에서는 인기 우선이며 native/keyword/genre 여러 질의를 합친다. 이 상태에서 마지막 배열만 날짜순으로 바꾸면 다음 공급자 페이지에 남은 최신작을 앞질러 구작을 반환한다.
- 실제 v23 로그의 2026-11-15 17:58~17:59 KST 실패 3건은 `Shutdown/CPUTime`, CPU2092/2260/2098ms와 HTTP546으로 연결됐다. `rankCandidates`가 후보마다 라이브러리의 신호/테마를 반복 정규화하고, 이유 생성과 신호 생성도 중복 수행했다.
- 24개는 상한이 아니다. 다음 목표는 36개이나 실패로 멈췄다. 현재 필터 서명/계정별 캐시 분리는 있으며, 조건 혼입의 주원인은 구작 보충 정책과 새 정책 버전 부재다.

## 3. 재현

1. 빈 검색, 국가 JP/KR, 최신 추천을 조회한다.
2. 첫 12개/추가24개에 먼 과거 인기작이 섞이고 후속 조회가546으로 실패한다.
3. 수정 후 같은 조건에서 최근 공개일의 적격 후보를 먼저 찾고 12→24→36으로 이어진다. 예산/장애로 중단해도 구작 보충으로 순간 이동하거나 전부 찾았다고 표시하지 않는다.

## 4. 설계 결정

### D-1. 최신 모드를 명시적으로 분리한다

새 앱은 추천 요청에 `discovery_mode:'latest'`를 보낸다. 서버는 같은 값을 확인 응답한다. 최신 모드에서는 전 기간 인기 취향 보충과 선조회 모두 사용하지 않는다. 기존 mixed 요청의 docs/41·52 계약은 호환 경로로 보존한다. 이번 사용자 요구는 새 최신 모드에 한해 docs/41 D-1/D-3/D-5/D-7·docs/52의 보충 선조회 결정을 대체한다.

### D-2. 공개일 기준으로 미소비 후보를 이어 찾는다

현재 공개일부터 월을 거슬러 탐색한다. 임의의 1년/6개월 필터는 추가하지 않는다. TV/영화/AniList 질의를 실제 공개일 내림차순으로 바꾸고, 공급자 내부 native/keyword/genre OR 질의도 독립된 페이지·raw offset으로 관리한다. 모든 스트림의 다음 후보를 비교해 가장 최신 후보부터 소비한다. 같은 날짜는 안정적인 스트림/identity 순서로 결정한다. 더 최신 후보를 다양성 할당 때문에 버리고 옛 작품으로 채우지 않는다. 취향 점수·이유/신호는 설명과 동률의 보조 정보다.

현재 월의 미확인/미소비 후보를 남겨둔 채 이전 월이나 전 기간 인기작으로 넘어가지 않는다. 요청한 월/공개 기준일과 명백히 다른 날짜의 후보는 거절한다. 날짜 미상·잘못된 일자를 최신작으로 추정하지 않는다.

### D-3. 안정적인 최신 커서와 실패 재개

`lc1.` 커서는 정책 버전, mode, 계정·정규화 필터/제외 설정의 SHA-256 scope, 유형, 공개 기준일, 월, 각 스트림의 page/raw offset/done/frontier와 페이지 fingerprint를 묶는다. fingerprint는 ID·순서·공개일·판정 메타데이터·hasMore의 SHA-256 앞 8바이트다. 중첩 객체의 키를 재귀 정렬한 canonical JSON을 해시하되 배열 순서와 실제 값은 보존한다. PostgreSQL JSONB 왕복의 객체 키 재배열을 내용 변경으로 오인하지 않는다. 커서의 `fingerprintPolicy:jsonb-canonical-v1`로 이전 raw-key-order 정책을 구별한다. 같은 페이지의 삽입/순서 변경이 offset 앞에서 일어나도 오류로 구별한다. 구 tf1·다른 계정/필터·지원하지 않는 버전은 명시적 invalid cursor 오류다. 원시 offset은 필터/키워드 검사 후 나온 배열의 인덱스와 혼동하지 않는다.

키워드 확인 예산이 부족하면 해당 head를 소비하지 않는다. 공급자 실패·순서 역행 등 최신 head를 확정할 수 없는 상황은 현재 결과/커서를 보존하고 명시적 재시도/처음부터 다시 찾기를 제공한다. 요청 예산 때문에 짧거나 빈 결과가 나와도 탐색이 남으면 has_more를 유지한다. 모두 소진했을 때만 종료다.

### D-4. 기존 조건과 안전장치 보존

한국어 제목, 국내 OTT 조건, 국가/장르/연도/유형, 하드 테마 제외, 등록 작품/현재 세션 중복 제외, 12개 묶음, 추가/완료 identity 검증·잠금·스냅샷, 요청 이유 집계와 자동 호출 상한을 유지한다. 노출 기록은 기존처럼 응답에 합쳐 저장한다. 사용자 기록·DB schema·RLS·secret은 변경하지 않는다.

### D-5. CPU는 같은 의미의 계산을 재사용해 줄인다

요청당 `createRecommendationLibraryContext` 한 번으로 양수 가중치·정규화 장르/인물/스튜디오/키워드·테마 색인을 만든다. 프로필/후보 순위/추천 이유가 이 context를 공유한다. 후보 신호는 한 번 계산해 이유와 응답에 같이 쓴다. 기존 기본 순위·신호 우선순위·값3개/제목2개·표시 문자열·점수·동률은 바꾸지 않는다. 새 `ordering:'latest'`일 때만 정확한 공개일을 우선한다.

### D-6. 새 정책과 과거 앱 데이터를 섞지 않는다

앱 Query namespace에 `latest-catalog-v1`을 넣어 이전 구작 보충 목록/커서를 재사용하지 않는다. 응답 mode 확인이 없으면 최신 정책 성공으로 표시하지 않고 자동 반복을 중단한다. invalid cursor는 같은 커서 재시도를 반복하지 않고 “처음부터 다시 찾기”를 제공한다. 기존 정상 “새 추천12개”의 다음 묶음 흐름과 별개다. 재시작 실패도 기존 목록을 보존한다.

> 설계 결정을 임의로 낮추지 않는다. 이 문서의 새 최신 모드가 대체한 항목 외 기존 계약은 보존한다.

## 5. 기각한 대안

- 앱의 현재 24개만 다시 정렬: 미탐색 최신 후보를 가져오지 못한다.
- 인기 discover URL에 날짜 sort만 변경: 여러 공급자/내부 질의의 후속 페이지에 남은 최신작이 누락된다.
- 연도 2026 하드코딩: 다음 해/사용자 연도 필터를 깨고 실제 전체 최신순 요구를 임의로 축소한다.
- 호출/타임아웃/자동 재시도 무제한 증가: CPU 중복과 구작 보충 원인을 해결하지 못한다.
- 제외/등록 검사를 완화: 사용자가 원하지 않는 작품이 재등장한다.
- 기존 mixed taste cursor의 미반환 후보 누락까지 리팩터링: 새 최신 경로는 이를 사용하지 않으며 별도 과제로 기록한다.

## 6. API·데이터 흐름

입력 `discovery_mode:'latest'` → 기존 인증/현재 계정 자료 준비 → 공용 라이브러리 context → 최신 스트림 페이지 캐시/미확인 head 검증 → 최신 후보12개 → 기존 OTT 부착·노출 저장 → 응답 mode/현재필터/커서/diagnostics. 최신 공급자 캐시 키는 기존 인기순 페이지와 분리한다. 같은 base provider/page의 OR 질의는 한 요청/캐시의 lane 결과를 공유한다.

## 7. DB·보안

기존 service-role 전용 공급자 메타데이터 캐시만 사용한다. 계정별 라이브러리/피드백/개인 결과를 공유 캐시에 넣지 않는다. 사용자 JWT/RLS 읽기·인증 선행을 유지한다. 배포 대상은 검증한 `personalized-recommendations` 한 함수와 그 공용 의존 소스이며 다른 운영 함수는 그대로다.

## 8. 화면

UI 규칙 UI-1~UI-13을 따른다. 설명은 현재 공개일부터 조건에 맞는 작품을 순서대로 찾는다는 의미로 표시한다. 추가 로딩/오류 때 기존 카드를 유지한다. 546을 단순 인터넷 연결 실패라고 단정하지 않는다. 정책 불일치/커서 오류는 고정 한국어 문구와 명시적 재시작으로 복구한다. 시간/키워드 예산에 따른 확인 보류는 기존 테마 확인 안내·이어 찾기로 표시하고, 실제 `failed_sources`가 있는 경우에만 제공처 실패 문구를 표시한다.

## 9. 엣지 케이스

최근 월이 적음·24개 이상·provider2페이지에 더 최신 후보·같은날·OR질의 중복·JP/KR다중국가·등록/하드제외·키워드 예산 중단·빈/실패 페이지·연도/계정/필터 변경·구cursor/과거cache·단일source 회복·큰 라이브러리·실패 후 기존 목록 보존을 검증한다.

## 11. 변경 파일

`recommendationLatestCatalog*`, 필요 최신 provider helper, `recommendationProviders*`, `recommendationEngine*`, `personalized-recommendations/index.ts`; 앱 recommendation service/hook/정책 helper/test·추천 Query key·검색 화면 최소 안내. 모바일 실측에서 41.5px였던 공용 `ErrorState` 재시도 버튼만 최소44pt로 보완한다. 구조는 docs/04·08, 진입점은 AGENTS/문서 목차, 검증/운영 적용은 development_next_steps에 기록한다.

## 12. 범위 밖

일반 작품명 검색·유사 작품 검색·metadata 영속 캐시·사용자 기록 쓰기·DB schema/secret·무관한 화면 개편. 실제 등록/삭제/진행 저장을 검증 목적으로 실행하지 않는다.

## 13. 검증의 한계

공급자의 일자/지역 메타데이터 오류 자체를 모두 교정하는 작업이 아니다. 고정 기준일의 10분 API 페이지 캐시를 이어 읽으며 현재 월에서 마지막으로 읽은 각 스트림 페이지를 검증한다(done 스트림도 포함). 이미 넘긴 이전 페이지/월을 전부 다시 조회하지 않으므로 그쪽에 나중에 추가된 공급자 데이터는 명시적 처음 조회부터 반영된다. 검사 중인 페이지의 순서 변경은 커서 재시작으로 복구한다. 로컬 CPU 비교는 운영 지연/CPU 한도 통과 보장이 아니므로 운영 로그와 실제 로그인 화면을 별도로 확인한다. 레거시 mixed 취향 보충 cursor의 선택 후 미반환 후보 누락은 최신 경로에서 사용하지 않는 기존 과제로 남긴다.

10장 신규 순수 회귀를 먼저 써 실패를 확인한다. 기존 mixed/등록/하드제외/추가guard·API호출 상한 테스트를 삭제/완화하지 않는다.

### STEP 2 — 계산 재사용

추천 라이브러리 context와 후보 신호 재사용을 구현하고 기존 출력과 깊은 비교한다. 실행시간 assertion 대신 접근/정규화 횟수로 선형성을 고정한다.

### STEP 3 — 최신 수집

독립 스트림 rawoffset과 lc1 cursor, 실제공개일 공급자 조회/cache, head 검증을 연결한다. legacy mixed를 유지하고 latest는 인기fill/선조회0이다. 새앱 요청/확인/키버전·명시적재시작을 연결한다.

### STEP 4 — 검증

npm test·typecheck·lint·웹 export·Edge Deno check·diff 공백 검사와 UI 추가 줄 토큰/Alert 검사를 한다. 실제handler/Query fixture로 호출수·실패·재개를 확인하고 운영 원본 백업/후보 SHA를 준비한다. 기존 규칙에 따라 운영 반영 승인 후 이 함수만 적용하고 다른 함수 버전·무인증401·실행 소스 일치를 확인한다.
